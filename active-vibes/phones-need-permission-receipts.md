# Phones Need Permission Receipts: Mobile Agents Must Show What They Touched

## Name

Phones Need Permission Receipts: Mobile Agents Must Show What They Touched

## Signal

**Verified:** A 2026 arXiv paper on mobile GUI-agent permission dialogs reports that task-completion-driven agents can grant unnecessary Android-style permissions and argues that task execution should be separated from permission authorization. Recent mobile GUI-agent papers also emphasize long-horizon task state, transition verification, real closed-source app benchmarks, and GUI world models.

## Intuition

The phone is the most personal computer, but mobile-agent research is still mostly optimizing task success. Once agents operate real apps, success is not enough. The missing consumer primitive is a readable receipt of what the agent saw, touched, granted, changed, and declined.

## Core Question

Can mobile AI become useful without making people feel that their phone has become porous?

## Emerging Capability

Mobile agents can increasingly infer app operations from demonstrations, maintain task state across apps, simulate GUI transitions, and act through screen pixels, UI trees, and touch actions.

## Current Assumption

If a mobile GUI agent completes the delegated task reliably, the product problem is mostly solved.

## Challenged Assumption

On phones, the primary constraint may be authorization literacy, not action competence. A correct task can still be a bad agent action if it quietly grants excess permissions, crosses app boundaries, leaks sensitive context, or cannot explain the path it took.

## Enabling Changes

- **Verified:** Apple App Intents documentation frames app actions and content as discoverable by Apple Intelligence, Siri, Spotlight, Shortcuts, and widgets.
- **Verified:** Android has explicit runtime permission systems, including notification permissions, and accessibility-service APIs that can observe and interact with interfaces under user-granted scope.
- **Verified:** Mobile GUI-agent research in 2026 is shifting toward state transitions, task-state representations, closed-source app evaluation, and permission-literacy studies.
- **Supported:** MCP and app-action ecosystems are normalizing tool/action descriptions, but phone-level consumer trust surfaces remain immature.

## Missing Primitive

A **Mobile Permission Receipt**:

- task requested
- apps entered
- screen classes observed, with redaction
- permissions encountered
- agent recommendation and user decision
- actual permission result
- data written, sent, deleted, or exported
- uncertain steps
- reversible steps
- follow-up cleanup suggestion

## Existing Evidence

- **Verified:** Chen et al. (2026), `2608.04755v1`, introduces Permission Literacy for mobile GUI agents and finds task context and requester identity can materially alter agent permission decisions.
- **Verified:** Zheng et al. (2026), `2607.00502v1`, proposes Task-State Representation with a progress tracker and transition-aware action verifier for long-horizon mobile GUI agents.
- **Verified:** Xu et al. (2026), `2608.05891v1`, proposes AppDeltaWorld, a transition-grounded mobile GUI world model that predicts reachable code updates rather than unconstrained next-screen images.
- **Verified:** Sui et al. (2026), `2605.27761v1`, introduces AndroidDaily across 350 tasks and 94 closed-source Android apps with process-aware diagnostic evaluation.
- **Verified:** Zhang et al. (2026), `2606.12817v2`, turns mobile screen trajectories into operational knowledge and uses a Teach-and-Repeat paradigm for reusable task automation.

## Contradicting Evidence

- **Supported:** Mobile operating systems already expose permission dialogs and user-controlled accessibility settings, so a separate receipt layer may feel redundant unless it is dramatically clearer than existing system logs.
- **Inferred:** Platform owners may absorb the best version of this primitive directly into OS-level AI surfaces, limiting standalone app defensibility.
- **Unknown:** It is not yet clear whether normal users will review receipts after routine delegated tasks, or only after something goes wrong.

## Open Questions

- What is the smallest receipt that changes user trust without becoming compliance noise?
- Should permission receipts be generated by the OS, the agent runtime, or the app being acted upon?
- How should receipts redact sensitive screens while preserving enough evidence to debug mistakes?
- Can receipts become a useful onboarding loop for teaching future agent behavior?
- What permission classes should always pause for human approval even when the task is urgent?

## Strange Implications

- The future phone assistant may need a memory of refusals more than a memory of preferences.
- App permissions become part of product taste: good apps will be easier for agents to enter, use, and exit cleanly.
- A phone could have an “agent audit roll” next to the camera roll: not memories of life, but memories of delegated control.
- Viral consumer agents may spread through receipts people can trust and share, not through demos of magic automation.

## Possible Experiments

1. Hand-author 10 Mobile Permission Receipts for common phone tasks: book a ride, reorder groceries, schedule a meeting, download a video draft, post a story, update a listing, return an item, mute notifications, share a file, and cancel a subscription.
2. Compare three receipt lengths: one-line, card, and detailed trace.
3. Test whether users can detect an over-permissioned action faster from a receipt than from screenshots alone.
4. Build a static mobile mock where an agent asks for a permission and the receipt predicts consequences before approval.

## Potential Outcomes

- Consumer app: a phone-agent trust layer for people delegating messy personal tasks.
- Developer tool: permission-receipt testing for apps that want to become agent-friendly.
- OS primitive: native audit cards for app intents, Shortcuts, and AI actions.
- Agent primitive: mobile analog to flight recorders, undo envelopes, and transition cards.

## Unexpected Connections

Mobile permission receipts resemble luggage tags more than security logs. A luggage tag does not expose the whole trip; it gives custody, route, owner, and recovery information at the moment something moves across boundaries. Phone agents need the same: not exhaustive surveillance of the user, but compact custody labels whenever agency crosses an app, permission, or data boundary.
