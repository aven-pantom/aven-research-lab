# DESIGN.md

## Purpose

This document defines the default design direction for products, apps, websites, dashboards, tools, and interfaces.

It should be used as a reusable design standard when starting a new product or reviewing an existing one.

The goal is not to create generic minimal software.

The goal is to create functional digital products composed with the discipline of a catalogue, the confidence of a poster, and the spatial logic of an instrument.

---

# 1. Core Design Position

The interface should feel:

Calm  
Precise  
Editorial  
Useful  
Structured  
Distinct  
Spatial  
Technical  
Premium  
Slightly unexpected

The product should feel visually minimal but intellectually dense.

It should hold a large amount of thought without showing visual anxiety.

The design must never feel like a default SaaS template, a raw component library, or a collection of disconnected cards.

Every screen should feel composed.

---

# 2. Primary Design Tension

The default tension is:

**Minimal on the surface, deeply involved underneath**

Other useful tensions include:

Editorial but functional  
Technical but human  
Rigid but expressive  
Quiet but powerful  
Familiar but strange  
Industrial but soft  
Dense but calm  
Precise but alive

Each product should choose one primary tension.

That tension should influence layout, typography, color, motion, copy, navigation, interaction, and brand expression.

When a design feels generic, strengthen the tension.

---

# 3. Design Philosophy

## 3.1 Design the product as an instrument

Do not design the interface as a collection of components.

Design it as a coherent instrument.

The user should feel that every control, panel, list, label, and transition belongs to the same system.

## 3.2 Clarity before decoration

A user should understand:

What this screen is  
What is happening  
What can be done  
What should happen next

Do not use visual style to cover weak hierarchy or information architecture.

## 3.3 Minimal does not mean empty

Whitespace is useful, but emptiness alone is not design.

The product can show a lot of information at once if that information is controlled through grid, alignment, hierarchy, spacing, type, grouping, and progressive disclosure.

## 3.4 Controlled density

Prefer interfaces that are rich in information but calm in presentation.

The user should be able to scan the product quickly without feeling overwhelmed.

Avoid excessive fragmentation.

## 3.5 First glance matters

A screen should communicate before it is read.

Use scale, position, contrast, grouping, spacing, repetition, image placement, and typographic rhythm.

The hierarchy should remain understandable when the screen is blurred or viewed from a distance.

---

# 4. Visual Language

## 4.1 Editorial utility

The product should behave like software but be composed like:

A catalogue  
A magazine  
A poster  
An index  
A technical manual  
A physical control surface

Information should feel placed, not poured into a layout.

## 4.2 The frame is part of the design

Treat the viewport, shell, browser frame, panel, canvas, or outer field as part of the composition.

The interface may sit inside:

A black field  
A soft grey field  
A browser style frame  
A rounded working surface  
A fixed desktop shell  
A spatial workspace

The product should feel like an object placed deliberately in space.

## 4.3 Quiet base, singular disruption

Use a restrained visual base.

Typical base:

White  
Off white  
Soft grey  
Black  
Charcoal  
Muted beige

Then introduce one strong disruption:

A vivid image  
One accent color  
One oversized word  
One unusual crop  
One material texture  
One bold interaction  
One unexpected spatial move

Do not make every part expressive.

## 4.4 Industrial softness

Combine rigid grids, technical text, lists, rules, numbering, and system controls with rounded surfaces, soft shadows, muted tones, subtle grain, calm spacing, and tactile motion.

The product should feel strict without becoming hostile.

## 4.5 Retro systems without imitation

Use inspiration from old terminals, print catalogues, desktop software, fashion indexes, editorial layouts, and industrial interfaces.

Do not recreate old software literally.

Recover its clarity, visible structure, and character.

---

# 5. Layout

## 5.1 Treat the viewport as a composition

Do not only ask where components should go.

Ask:

Where is the visual weight?  
Where is the silence?  
Where does the eye begin?  
Where does it move next?  
What breaks the structure?

Every screen should have one dominant composition.

## 5.2 Prefer fewer, stronger regions

A screen should usually contain:

An orientation area  
A primary working area  
A secondary context area  
A restrained action area

Avoid dividing the screen into many equal cards.

## 5.3 Use strong grids

The grid should remain visible through alignment, rules, numbering, columns, repeated rhythm, consistent offsets, and structured whitespace.

The grid should not always be hidden.

It can become part of the identity.

## 5.4 Use asymmetry deliberately

Perfect symmetry often feels generic.

Useful patterns include:

Information on the left, work on the right  
Dense top, open bottom  
Large object beside small metadata  
Centered object with off axis controls  
Narrow rail beside a wide canvas  
Image interrupting a strict list  
Quiet field beside a dense panel

The imbalance should feel controlled.

## 5.5 Avoid unnecessary vertical stacking

Core workflows should not become one long column.

Prefer split views, side rails, inspectors, timelines, persistent controls, tabbed regions, overlays, context panels, and spatial workspaces.

Keep important context visible.

## 5.6 Avoid nested containers

Do not place cards inside cards inside panels.

Use spacing, alignment, background changes, typography, rules, and position before adding another container.

---

# 6. Typography

Typography should carry most of the visual hierarchy.

## 6.1 Type roles

Use a limited but clear type system:

Display type for major moments  
Large heading for orientation  
Medium heading for sections  
Body type for explanation  
Small type for metadata  
Monospace for technical values, logs, identifiers, and system states

## 6.2 Typography as interface

Typography is not decoration.

Use it to create navigation, hierarchy, rhythm, identity, state, grouping, and focus.

Useful devices include:

Large editorial headlines  
Compact sans serif navigation  
Numbered indexes  
Uppercase labels  
Monospace values  
Wide line breaks  
Small metadata beside large content

## 6.3 Strong scale contrast

Use real contrast between levels.

Do not make every text size only slightly different.

A large headline can sit beside very small metadata.

This creates confidence and editorial tension.

## 6.4 Short, direct copy

Use concise product language.

Prefer:

Create model  
Run analysis  
Open project  
Export clip  
Add source  
View results

Avoid:

Get started  
Continue  
Proceed  
Learn more  
Unlock your potential

## 6.5 Avoid tiny text as a luxury signal

Small text should support hierarchy.

It should never become difficult to read simply to make the interface feel premium.

---

# 7. Color

Use a restrained palette.

## 7.1 Default palette structure

Background  
Primary text  
Secondary text  
Surface tone  
Border tone  
One accent  
Status colors

## 7.2 Use color with purpose

Color should indicate state, focus, action, identity, selection, urgency, or system feedback.

Do not use many accent colors to make the interface feel active.

## 7.3 Accent discipline

Most screens should have one dominant accent.

Examples:

Orange on cream  
Red on white  
Green on grey  
Blue on black

The accent should feel intentional and memorable.

## 7.4 Avoid generic gradients

Do not use bright gradients unless the product concept truly requires them.

---

# 8. Imagery

## 8.1 Images should interrupt structure

Do not always place images inside predictable cards.

Images may be:

Cropped  
Suspended  
Overlaid  
Offset  
Partially hidden  
Placed over type  
Inserted into lists  
Used as visual punctuation

## 8.2 Image and information tension

Combine expressive imagery with highly ordered information.

The image brings life.

The system brings control.

## 8.3 Use fewer, stronger images

One well placed image is often stronger than many thumbnails.

Use repeated images only when repetition is part of the information model.

---

# 9. Components

## 9.1 Components must belong to the product

Do not ship raw component library styling.

Revise spacing, radius, borders, typography, hover behavior, focus behavior, icon weight, density, motion, and state treatment.

## 9.2 Cards are for objects

Use cards when they represent meaningful units:

Projects  
Files  
Models  
People  
Results  
Sessions  
Products  
Saved items

Do not use cards as generic decoration.

## 9.3 Prefer lists, indexes, and tables

For structured information, prefer lists, indexes, tables, rows, columns, numbered collections, and spatial groupings over endless card grids.

## 9.4 Borders are construction lines

Use borders to reveal structure.

Borders should define sections, rows, selection, alignment, hierarchy, and spatial logic.

Do not use borders only as decoration.

## 9.5 Selective corner radius

Not everything should be rounded.

Use radius to indicate touch, containment, softness, floating layers, temporary panels, and physicality.

Keep structural areas sharper where appropriate.

## 9.6 Buttons

Primary buttons should be obvious but not oversized.

Secondary actions should stay quiet.

Destructive actions should not compete with productive actions.

Use icon only buttons only when context makes the action obvious.

## 9.7 Inputs

Inputs should feel intentional and calm.

Use helpful defaults, examples, inline guidance, clear states, and direct manipulation where possible.

Avoid long form driven workflows when users can manipulate the object directly.

---

# 10. Navigation

## 10.1 Keep navigation quiet

Navigation should support the composition.

It should not dominate the product unless navigation itself is the main task.

## 10.2 Use compact structures

Useful patterns:

Thin top bars  
Side rails  
Numbered sections  
Index based navigation  
Category lists  
Persistent contextual menus  
Small labels with strong alignment

## 10.3 Keep context visible

Do not force users to repeatedly leave the working area.

Prefer persistent navigation, split views, side panels, inline expansion, drawers, overlays, and context menus.

## 10.4 Avoid menu inflation

Do not create too many top level destinations.

Group by how users think and work.

---

# 11. Spatial Interfaces

Panels should behave like physical parts of a system.

Useful surfaces include:

Side rails  
Inspectors  
Search overlays  
Command menus  
Context menus  
Floating controls  
Timelines  
Trays  
Canvases  
Docked panels

These elements should feel assembled, not stacked.

Each panel should have a clear role.

---

# 12. Interaction Design

## 12.1 Immediate feedback

Every action should produce visible feedback.

Show loading, progress, success, failure, saved state, unsaved state, background activity, empty state, disabled state, and selection.

The user should never wonder whether the product received the action.

## 12.2 Prefer direct manipulation

When possible, allow users to drag, resize, connect, scrub, reorder, select, preview, edit in place, and move through space.

Use inspectors for precision, not as the only control method.

## 12.3 Keep power close

Advanced functionality should remain nearby.

Use expandable regions, command menus, keyboard shortcuts, context menus, inspectors, inline controls, and secondary panels.

Do not bury serious functionality in distant settings pages.

## 12.4 Preserve context

Avoid unnecessary page transitions.

Keep the user oriented while changing state.

---

# 13. Search, Filters, and Command Surfaces

Search, filters, and command menus are primary design surfaces.

They should not feel secondary or generic.

## 13.1 Search surfaces

A search interface may include:

Recent queries  
Suggested people or objects  
Categories  
Quick filters  
Trending items  
Saved searches  
Keyboard actions

## 13.2 Filtering

Filters should feel like part of the information architecture.

Use visible categories, numbered sections, inline tags, structured lists, persistent filter rails, and clear active states.

Avoid opening a generic modal containing dozens of checkboxes.

## 13.3 Command menus

Command menus should feel fast, compact, and serious.

Use clear groupings, shortcut hints, strong selection states, nested actions only when necessary, and minimal visual noise.

---

# 14. Motion

Motion should explain change.

Use motion to show:

Where an object came from  
Where it moved  
What changed  
What is active  
What became available  
What is connected  
What is processing

Motion should feel controlled, smooth, understated, responsive, and precise.

Avoid excessive bounce and playful spring motion.

Fast actions should feel fast.

Important transitions can feel more cinematic.

---

# 15. Responsive Design

Responsive design should preserve hierarchy, not simply stack everything.

## Desktop

Use split views, wide canvases, persistent context, dense workspaces, inspectors, and multiple information layers.

## Mobile

Use one main task at a time, clear navigation, bottom anchored actions, progressive disclosure, touch friendly controls, and focused information density.

Do not shrink desktop layouts into narrow columns.

Redesign the workflow for the device.

---

# 16. Empty States

Empty states should teach the product.

They should explain:

What this area is  
Why it is empty  
What the user can do next  
What a completed state may look like

Avoid vague copy such as:

Nothing here yet

Use the empty state to reveal the product model.

---

# 17. Loading and Progress

Loading should feel integrated into the system.

Use inline progress, skeleton structures, system status, progress labels, background processing indicators, and visible task queues.

Avoid blocking the entire product unless necessary.

The user should understand what is happening and whether they can continue working.

---

# 18. Errors

Errors should explain:

What happened  
Why it matters  
What remains safe  
What the user can do next

Use calm, direct language.

Do not blame the user.

Do not expose technical details unless they help solve the problem.

---

# 19. Icons and Graphics

Use icons sparingly.

Icons should support recognition, not replace clear language.

Maintain consistency in stroke, weight, corner treatment, optical size, and level of detail.

Custom graphics should feel structural, technical, editorial, systemic, and product specific.

Avoid random abstract blobs and generic 3D illustrations.

---

# 20. Product Worldbuilding

A strong product should feel like it belongs to a world.

The same visual logic should appear across:

Interface  
Website  
Documentation  
Posters  
Loading states  
Empty states  
Icons  
Illustrations  
Launch materials  
Product screenshots  
Error messages  
System copy

The product should remain recognizable without the logo.

Worldbuilding should come from repeated rules, not random decoration.

---

# 21. Screen Design Process

For each screen:

## Step 1. Define the job

Write one sentence describing what the user must accomplish.

## Step 2. Define the hierarchy

Identify:

Primary object  
Primary action  
Secondary actions  
Current state  
Supporting information

## Step 3. Choose the composition

Decide the visual balance.

Examples:

Dense left, open right  
Object centered, controls peripheral  
Quiet top, active bottom  
Stable shell, changing canvas  
Image interrupting a list  
Narrow rail beside a wide field

## Step 4. Remove generic patterns

Check for:

Too many cards  
Default dashboard layouts  
Unnecessary pills  
Generic gradients  
Overused icons  
Predictable hero structures  
Component library appearance

## Step 5. Add one memorable move

Examples:

Unexpected information placement  
Strong typographic scale  
A persistent system status  
A spatial interaction  
A signature transition  
A custom preview behavior  
An unusual crop  
A unique empty state

## Step 6. Test the first glance

Blur or zoom out.

The hierarchy should remain obvious.

## Step 7. Test real content

Use long names, dense data, empty states, errors, loading, small screens, large screens, and extreme values.

Never approve a screen using only short placeholder text.

---

# 22. Default Starting Direction

When no product direction has been defined, begin with:

Neutral light or dark base  
Strong typography  
Visible grid logic  
Large working areas  
Minimal borders  
Selective radius  
One accent color  
Technical metadata  
Editorial spacing  
Compact navigation  
Clear system status  
Subtle motion  
One distinctive interaction  
A composed first viewport  
A layout that shows the product immediately

---

# 23. What to Avoid

Avoid:

Generic SaaS dashboards  
Too many cards  
Cards inside cards  
Excessive rounded rectangles  
Random glassmorphism  
Bright startup gradients  
Overuse of pills  
Centered text everywhere  
Weak hierarchy  
Tiny unreadable text  
Large empty hero sections  
Unnecessary modals  
Decorative charts  
Icons without labels  
Too many colors  
Too many font sizes  
Long onboarding flows  
Marketing copy inside the product  
Animations that interrupt work  
Every screen using the same layout  
Minimalism replacing usefulness  
Softness without structure  
Structure without personality  
Images trapped inside predictable cards  
Raw component library styling

---

# 24. Quality Checklist

Before approving a design, confirm:

The main action is obvious  
The screen has one dominant idea  
The first glance communicates hierarchy  
The layout feels composed  
The interface does not look like a template  
The grid is intentional  
The density feels controlled  
Typography carries hierarchy  
The accent color has a purpose  
The product works with real content  
Loading, empty, error, and success states exist  
The interaction model is clear  
The system preserves context  
The mobile version is intentionally redesigned  
Every visible element earns its place  
The product tension is visible  
One memorable move exists  
The design feels useful before it feels impressive  
The product remains recognizable without its logo

---

# 25. Final Rule

Do not design software as a page filled with components.

Design a coherent digital object.

Every screen, word, image, interaction, state, and transition should reinforce how the product thinks.
