# Field Notes — 2026-08-12 — App Action Maps

- **Signal:** App Intents, Android shortcuts/App Actions, WebDriver BiDi, MCP, accessibility automation, and computer-use agents are all trying to make software operable by machines from different layers.
- **Odd convergence:** OS vendors expose intents/shortcuts; browser standards expose automation events; agent protocols expose tools/resources; model labs expose screen-use agents. None alone tells an agent what an app’s actions mean in the current state.
- **Useful phrase:** Action Map Card — an app’s objects, verbs, preconditions, risks, expected deltas, undo paths, stale markers, and receipts.
- **Contradiction:** The more general the agent interface becomes, the more it needs local semantic orientation. Pixels are universal but semantically expensive.
- **Researcher/platforms worth tracking:** Apple App Intents, Android App Actions/Shortcuts, W3C WebDriver BiDi, MCP, Anthropic computer use, browser accessibility APIs.
- **Question:** Can app action maps be generated from existing intent/tool schemas and then refined by observed receipts?
- **Rejected path:** Do not frame this as “every app needs an API.” APIs expose operations; action maps orient delegated work.
