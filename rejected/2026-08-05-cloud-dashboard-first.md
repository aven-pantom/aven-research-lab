# Rejected Path — Cloud Dashboard First

Date: 2026-08-05

## Why it initially seemed promising

The browser-database signal could easily become a generic "local-first dashboard builder" or a lightweight Airtable/Notion clone. That path sounds useful because many personal workflows need tables, filters, saved views, and lightweight automation.

## What weakened it

- **Supported:** Dashboard builders and low-code tables already exist as familiar categories.
- **Inferred:** Starting with a generic builder would hide the more interesting primitive: custody plus receipts around a bounded personal workshop.
- **Inferred:** Backend-first or dashboard-first framing would pull the work toward accounts, templates, sharing, and productivity aesthetics before the local artifact is validated.

## Failed assumption

The failed assumption is that the opportunity is "make app building easier." The stronger assumption is narrower: make one local working world trustworthy, inspectable, exportable, and safe for agents to mutate.

## Useful remnants

- Saved views are still important.
- Simple schemas are still important.
- Import/export matters more than template libraries.
- Collaboration can come later as an adapter, not as the starting architecture.

## Future signal for reconsideration

Reconsider a broader builder only after at least three successful Single-File Workshop Cards converge on the same custody, schema, receipt, and export primitives.
