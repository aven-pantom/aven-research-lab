# Unexpected Connection — Taste Compilers and Design Tokens

## Connection

Personal taste and design systems share a hidden transition: examples must become constraints before they can travel.

A moodboard is to personal style what a screenshot folder is to a design system. It points at a world, but it does not say which properties are protected, which can mutate, which combinations are forbidden, or how to test whether a new artifact still belongs.

## Shared structure

- **Examples are ambiguous.** A saved outfit might mean color, silhouette, attitude, pose, brand, occasion, or only one detail.
- **Rules carry taste across contexts.** Design tokens let teams reuse visual law across products; Taste Constraint Cards could let people reuse personal aesthetic law across apps.
- **Negative constraints matter.** A design system is partly made of forbidden states. Personal style is partly made of things that almost work but should not pass.
- **Compilation is interpretive.** The hard work is not storage. It is deciding which properties survive translation.

## Mechanism transfer

Design-token practice suggests Taste Constraint Cards should separate:

- raw references,
- extracted properties,
- semantic roles,
- allowed variants,
- forbidden states,
- usage context,
- review tests,
- deprecation / expiry.

## Why this matters

Most taste apps start with recommendations or generated outputs. Design systems suggest the opposite sequence: first compile the law of the world, then use tools to make new artifacts that can be judged against it.

## Evidence label

**Inferred:** The connection is structural. This session verified sources around fashion recommendation, creative tools, and existing prior lab design/taste primitives; it did not perform a separate literature scan on design-token systems.
